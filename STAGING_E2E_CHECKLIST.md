# DCXORA — Staging end-to-end release checklist

**Purpose:** verify the real product flow and failure behavior against an isolated staging environment. This checklist is deliberately separate from CI: automated tests use mock/placeholder configuration and do not prove that a live provider, database, object store, payment webhook, or export is working.

## Release-safety preflight

- [ ] Use a staging deployment, staging Supabase/Postgres database, and a separate private `project-assets` bucket. Do not use production credentials or production customer data.
- [ ] Back up the staging database and inspect its actual applied-migration ledger/schema before changing it.
- [ ] Review duplicate numeric migration prefixes and legacy billing SQL; do not apply SQL files by filename alone or assume Drizzle's journal covers every migration.
- [ ] Review and apply only the missing migrations required by this branch in dependency order, starting with the job pipeline functions used by the running code. At minimum inspect dependencies for `0013`, `0015`–`0024`; verify each is already applied or reviewed/applied in staging before testing dependent features.
- [ ] Configure valid staging credentials for Supabase, `LOVABLE_API_KEY`, the staging renderer (`SHOTSTACK_ENV=stage` or a staging `RENDERER_URL`), and any voice/Paddle sandbox integrations being tested.
- [ ] Confirm browser-exposed variables contain publishable configuration only. Never use a secret in a `VITE_*` variable.
- [ ] Create two test users (User A and User B), plus a staging administrator. Use test credits and provider accounts that can incur only approved test costs.
- [ ] Record the tested branch commit, environment, migration ledger, provider/model names, test timestamps, and evidence. Redact bearer tokens, signed URLs, API keys, passwords, and payment data.

## A. Authentication, projects, and scene persistence

- [ ] Register User A, verify login/logout and session expiry behavior, then sign in again.
- [ ] Create a project with a title, idea, format, aspect ratio, and duration. Refresh the page and confirm the project settings persist.
- [ ] Generate a structured script/scene outline. Confirm scene count, title, narration, visual prompts, duration bounds, and ordering are valid.
- [ ] Refresh and reopen the project. Confirm scenes persist without duplicate rows.
- [ ] Edit a scene, reorder scenes, delete one, and reload. Confirm updates persist and positions remain normalized.
- [ ] Save a project version, change scenes, restore the version, and confirm the restored scene list and asset references are valid.
- [ ] Create a separate project as User B. Confirm User B cannot read or mutate User A's project or its scenes.

## B. AI scene drafting and job settlement

- [ ] Run scene drafting successfully. Confirm the job reaches a terminal `complete` state and the returned scene rows appear after a refresh.
- [ ] Force an AI-provider timeout or malformed structured response. Confirm the UI leaves no permanent spinner and the job reaches a checked terminal failure state.
- [ ] Simulate a scene-count query failure and a scene-insert failure. Confirm a failure is surfaced rather than reported as success.
- [ ] Simulate the insert succeeding while its response is lost (or use a controlled mock). Confirm cleanup targets only the newly generated scene IDs, not existing project scenes.
- [ ] Simulate the completion RPC failing twice after scenes are inserted, with checked failure settlement confirming the job failed. Confirm only the new rows are removed; inspect job events and credit transactions.
- [ ] Simulate settlement or cleanup being unavailable. Confirm the app reports reconciliation/cleanup uncertainty and does not falsely claim a refund or delete potentially referenced output.
- [ ] Simulate the completion response being lost after the job actually completed. Confirm the app reconciles the terminal state and preserves successful output.

## C. Video clip generation — critical gate

For each scenario, record the job ID, result, asset row, scene reference, credit-ledger evidence, and relevant redacted logs.

- [ ] Happy path: generate a clip for a scene with a non-empty visual prompt. Confirm the provider job ID is saved and the job does not block the initial HTTP response waiting for the complete video.
- [ ] Poll the provider until completion. Confirm the generated bytes pass MP4-compatible MIME and ISO BMFF container checks before upload/asset registration/completion.
- [ ] Verify the stored object uses the expected project/user-scoped path, an asset row points to it, the intended scene's `clip_path` matches it, and the job output references the same asset/path.
- [ ] Open/reload the scene and play the stored clip. Do not treat a green job status or a successful URL fetch as proof that the video decodes.
- [ ] Download/play the result and inspect with a media tool such as `ffprobe` when available. Confirm codec, dimensions, duration, and that the file is not an HTML/error payload renamed to `.mp4`.
- [ ] Test each supported provider result shape: top-level URL, `video_url`, `video.url`, `output.url`, and no URL requiring the authenticated provider-content endpoint.
- [ ] Return a stale/expired or malformed output URL while the authenticated content endpoint works. Confirm the valid fallback output is used.
- [ ] Return invalid/non-MP4 bytes, HTML, a wrong content type, truncated MP4 boxes, an empty media-data box, and a response over the 128 MiB cap. Confirm invalid data never becomes a completed scene asset.
- [ ] Simulate provider start timeout, missing provider job ID, provider HTTP 429/5xx, terminal provider failure, poll timeout, and the 15-minute overall deadline.
- [ ] Simulate URL download failure followed by authenticated-content success, then failure of both paths. Confirm the job ends in a visible terminal state and credit settlement is accurate.
- [ ] Simulate storage upload failure, asset-row insert failure, scene attachment failure, completion RPC failure after the scene is attached, and cleanup failure. Confirm compensation does not delete media while the database may still reference it.
- [ ] Poll the same completed job concurrently from two sessions. Confirm the atomic download claim prevents duplicate downloads/assets and duplicate credit settlement.
- [ ] Confirm a failed job's UI does not claim that credits were refunded unless the settlement outcome actually confirms a refund. Check the credit ledger and balance in staging.

## D. Voice, captions, timeline, and render

- [ ] Generate voiceover for a scene. Confirm audio storage, asset registration, scene/timeline association, playback, and checked job settlement.
- [ ] Force voice storage/association/completion failures. Confirm rollback preserves any media that may still be referenced and refund messages match the confirmed database result.
- [ ] Generate captions from audio/transcript. Edit caption text and timing; refresh and verify persistence and timeline bounds.
- [ ] Add video, voice, music, text, and captions to the timeline. Save edits, trim/reorder clips where supported, and verify the timeline after reload.
- [ ] Start a render and confirm the request returns a job ID without waiting synchronously for the render.
- [ ] Check queued/processing/progress/success/failure states. Test renderer timeout, provider failure, missing output URL, download timeout, bad content type, oversized output, malformed MP4, and finalization retry/race.
- [ ] Confirm an invalid render output is not marked ready. A valid render must have a stored export row and private media object with consistent metadata.
- [ ] Download the MP4 from the application and play it in a separate player/browser. Confirm duration, audio, captions, and aspect ratio; do not sign off on container-box validation alone.

## E. Export, share, billing, and admin

- [ ] Create a share link for a ready export. Test unlisted/private behavior, optional password, expiration, failed-password lockout, revocation, and signed URL expiry.
- [ ] Confirm a share page exposes only the selected ready export and does not expose permanent private storage credentials.
- [ ] In Paddle sandbox, test checkout completion, valid/invalid webhook signatures, duplicate event delivery, subscription changes/cancellation, failed payment handling, and credit-ledger reconciliation.
- [ ] Confirm credit reservations, charges, and refunds are server-authoritative and idempotent. Do not test live-money flows with this checklist.
- [ ] As a normal user, attempt to access User B's project, scene, asset, generation job, render job, export, sharing records, and billing data. Each unauthorized request must fail.
- [ ] As a non-admin, attempt to access admin users/jobs/credits/settings. Confirm access is denied and privileged mutations are audited.
- [ ] Confirm logs include useful job IDs/stages/error codes while redacting API keys, signed URLs, access tokens, and payment details.

## F. Scale and release decision

- [ ] Test projects with 10, 50, and 100 scenes, and libraries with 500 and 1,000 assets. Confirm pagination/lazy loading and the editor remain usable.
- [ ] Check browser console/network logs for failed requests, stale UI state, unhandled promise rejections, and permanent loading indicators.
- [ ] Re-run the CI workflow on the exact candidate commit after all code and migration changes.
- [ ] Confirm backup/restore and media-retention procedures for staging have been exercised.

## Sign-off rule

Mark every step `PASS`, `FAIL`, or `BLOCKED` with evidence. Do not call the app production-ready while any required core flow is blocked or failing. A local/CI pass is not a substitute for provider-backed generation, database/storage integration, real MP4 playback, cross-user authorization, and billing sandbox verification.
